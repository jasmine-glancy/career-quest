# Runbook: Core Data Model (Issue #1)

This runbook stands up the Postgres-backed core data model for Career Quest:
Users, Companies, Resumes, ResumeVersions, Jobs, Applications, Skills, and Notes.

## Prerequisites

- Docker Desktop (for PostgreSQL)
- Python 3.11+

## 1. Configure environment variables

From the repo root:

```
copy .env.example .env       # Windows
# cp .env.example .env       # macOS/Linux
```

Edit `.env` and set real local values for `POSTGRES_USER`, `POSTGRES_PASSWORD`, and
`DATABASE_URL` (the credentials in `DATABASE_URL` must match `POSTGRES_USER`/
`POSTGRES_PASSWORD`). `.env` is gitignored — it is never committed, and there are no
credential defaults baked into `docker-compose.yml` or `app/config.py`, so this step
is required before anything below will start.

## 2. Start Postgres

```
docker compose up -d
```

This starts a `postgres:16-alpine` container on `localhost:5432`, reading its
credentials from the root `.env` file, backed by a named volume so data survives
restarts.

Check it's healthy (substitute the `POSTGRES_USER` value you set in `.env`):

```
docker exec career-quest-postgres pg_isready -U <POSTGRES_USER>
```

## 3. Set up the backend environment

```
cd backend
python -m venv venv
venv\Scripts\activate        # Windows
# source venv/bin/activate   # macOS/Linux
pip install -r requirements.txt
```

`app/config.py` reads `DATABASE_URL` from the root `.env` (via `pydantic-settings`,
`env_file = "../.env"` relative to `backend/`) — no separate `backend/.env` needed.

## 4. Run migrations

```
alembic upgrade head
```

This creates all tables defined under `app/models/` (see `alembic/versions/` for the
autogenerated migration). To generate a new migration after changing models:

```
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

## 5. Seed sample data

```
python seed.py
```

Inserts one user, one company, one job (with three linked skills), a resume with one
version, an application tying it all together, and a note — enough to exercise every
table and relationship in the schema.

## 6. Verify

```
docker exec career-quest-postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB> -c "\dt"
```

Should list: `users`, `companies`, `resumes`, `resume_versions`, `jobs`, `applications`,
`skills`, `notes`, `job_skills`, `resume_version_skills`, `alembic_version`.

To inspect the seeded data directly:

```
docker exec career-quest-postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB> -c ^
  "SELECT a.application_id, u.name, j.title, c.name AS company, a.status FROM applications a JOIN users u ON u.user_id=a.user_id JOIN jobs j ON j.job_id=a.job_id JOIN companies c ON c.company_id=j.company_id;"
```

## Tearing down

```
docker compose down        # stop the container, keep data volume
docker compose down -v     # stop and delete the data volume
```

## Schema notes

- `resume_version_skills` and `job_skills` are many-to-many join tables so the future
  Job-Fit AI Analyzer (Issue #6) can diff a resume version's skills against a job's
  required skills.
- `Application.status` is a Postgres enum (`saved`, `applied`, `interviewing`, `offer`,
  `rejected`) matching the pipeline described in the README.
- `Note` is attachable to a user generally, or scoped to a specific application via an
  optional `application_id`.
- `ResumeVersion.snapshot_json` stores the full structured resume snapshot (experience,
  skills, education) as JSON so historical versions remain immutable.
